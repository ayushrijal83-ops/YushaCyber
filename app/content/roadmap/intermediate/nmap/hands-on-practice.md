# Nmap in Practice

## 1. What You Will Learn

By the end of this lesson you should be able to:

- run a real, authorized reconnaissance investigation from first discovery to a documented conclusion
- ask, and answer, the six questions that structure an enumeration mindset
- perform host discovery, basic scanning, targeted scanning, range scanning, and service/version detection against a real lab network
- interpret genuine scan output — including a filtered port and a host that blocks discovery probes — rather than memorized examples
- write an evidence-based investigation conclusion, distinct from jumping straight to "attack it"
- explain the authorization boundary around scanning, and what scan traffic can trigger on a real network
- place Nmap correctly inside the larger security methodology this roadmap builds toward

## 2. Why This Matters

Core Concepts taught you what each command asks and what kind of evidence it returns. This lesson is where those separate pieces become one investigation — the actual shape of real reconnaissance work, where you don't run commands in a fixed order from a worksheet, you run the next command *because of what the last one told you*. That's the skill this whole module has been building toward, and it's the skill every later module on this roadmap — Wireshark, Burp Suite, OWASP Top 10, and eventually the Red Team track — assumes you already have.

## 3. The Enumeration Mindset

Before touching a single command, hold these six questions in your head. They're the actual structure of everything that follows:

1. **Is the host alive?**
2. **Which ports are open?**
3. **What services appear to be running?**
4. **What versions are detected?**
5. **What network behavior is unusual?**
6. **What should I investigate next?**

Notice what's not on that list: "how do I break in." A student looking at

```
22/tcp open ssh
80/tcp open http
443/tcp open https
```

should reason **"there are at least three reachable services worth investigating"** — not **"immediately exploit port 22."** This module ends at question 6. Deciding what's actually worth investigating, and investigating it safely and legally, is real skill — attacking anything is a different module, with its own authorization requirements, later in this roadmap.

## 4. Security Ethics and Authorization

Read this before you run anything below.

**Only scan systems you own, or are explicitly authorized to test.** Every target in this lesson is part of this platform's own simulated lab network — nothing you run here ever reaches a real host, a real IP address, or the real internet. That's deliberate, and it's also the boundary you must carry with you off this platform: the techniques in this module are identical whether you're scanning an authorized lab or someone else's production server, but the second one is a crime in most jurisdictions regardless of your intent.

Scanning generates real, observable network traffic, and on a real network that traffic has consequences. It can trigger:

- **IDS/IPS** (intrusion detection/prevention systems) — built specifically to notice scan patterns
- **Firewall logging and alerts** — even a single blocked probe can be logged and reviewed
- **SIEM events** — scan traffic is a classic, well-known pattern that security teams actively watch for
- **Rate limits** — aggressive scanning can get your source address throttled or blocked outright
- **Human attention** — someone monitoring that network may simply notice and start asking questions

None of this is a reason to fear scanning an environment you're actually authorized to test — it's a reason to understand what you're doing before you do it. This module never frames evading any of the above as a goal. Section 13 of Core Concepts already told you a SYN scan is not invisible; that's not a limitation to work around, it's how a properly monitored network is supposed to work.

## 6. Exercise 1 — Host Discovery

**Objective:** Determine which hosts on the lab network are actually alive, before investigating any one of them individually.

**Command:**

```
nmap -sn 10.10.10.0/24
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.1
Host is up.

Nmap scan report for 10.10.10.10
Host is up.

Nmap scan report for 10.10.10.20
Host is up.

Nmap scan report for 10.10.10.30
Host is up.

Nmap scan report for 10.10.10.53
Host is up.

Nmap done: 6 IP addresses (5 hosts up) scanned.
```

**Expected reasoning:** This is question 1 of the enumeration mindset — before you invest time investigating any single host, find out which ones exist at all. `10.10.10.0/24` sweeps the entire training subnet in one command.

**Evidence interpretation:** Five hosts answered; the sixth (you'll meet it in Exercise 6) did not — and per Introduction §8, that does *not* yet mean it's irrelevant. You now have four real targets worth investigating (`.1` is the gateway, not usually a primary target) and one open question.

**Common mistake:** Treating this result as final. A "no" here is a *discovery-probe* result, not necessarily a statement about the host's actual services — Exercise 6 proves that directly.

## 7. Exercise 2 — Find Open Ports

**Objective:** Run a basic scan against the web server and find out which ports respond.

**Command:**

```
nmap 10.10.10.10
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.10

PORT     STATE    SERVICE
22/tcp open ssh
80/tcp open http
443/tcp open https

Nmap done.
```

**Expected reasoning:** This answers question 2. Three ports responded as open. You do not yet know what's actually running behind them — the `SERVICE` column is still just the port-number convention (Core Concepts §3), not confirmed evidence.

**Evidence interpretation:** Three reachable services worth investigating: one on the SSH-conventional port, two on the HTTP/HTTPS-conventional ports. That's it — that's the whole claim this evidence supports right now.

**Common mistake:** Reading `22/tcp open ssh` as "SSH is confirmed running." It's a label, not a confirmation — Exercise 5 is what actually strengthens that claim.

## 8. Exercise 3 — Scan a Specific Port

**Objective:** You already suspect the file server is running SSH. Confirm just that one port, without re-scanning everything else.

**Command:**

```
nmap -p 22 10.10.10.30
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.30

PORT     STATE    SERVICE
22/tcp open ssh

Nmap done.
```

**Expected reasoning:** This is a deliberately narrow question, asked because you already had a specific reason to ask it (Core Concepts §4). It's faster than a full scan and gives you exactly the one answer you needed.

**Evidence interpretation:** Confirmed: port 22 is open on the file server too. But a single-port scan, by design, tells you nothing about any other port on this host — which is exactly the gap Exercise 4 closes.

**Common mistake:** Concluding "port 22 is the only open port on this host" from a scan that only ever asked about port 22. A targeted scan answers a targeted question — nothing broader.

## 9. Exercise 4 — Scan a Range

**Objective:** The file server might be running more than SSH. Widen the investigation to a range that covers it.

**Command:**

```
nmap -p 20-30 10.10.10.30
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.30

PORT     STATE    SERVICE
20/tcp closed unknown
21/tcp open ftp
22/tcp open ssh
23/tcp closed unknown
24/tcp closed unknown
25/tcp filtered unknown
26/tcp closed unknown
27/tcp closed unknown
28/tcp closed unknown
29/tcp closed unknown
30/tcp closed unknown

Nmap done.
```

**Expected reasoning:** This is exactly the payoff Core Concepts §5 promised: widening the scope revealed something the single-port scan in Exercise 3 could never have found.

**Evidence interpretation:** Two new facts. An **open** FTP port (21) — a real second service on this host you didn't know about. And a **filtered** port (25) — Nmap cannot determine whether anything is there. Per Introduction §7, that is not the same as "nothing is there." It's an open question, not a closed one.

**Common mistake:** Writing off port 25 as "closed, so nothing to investigate." Filtered means unresolved — the honest conclusion is "I don't yet know," not "there's nothing here."

## 10. Exercise 5 — Identify Services and Versions

**Objective:** Strengthen the evidence on both hosts you've investigated so far — find out what's actually running, not just what's open.

**Command:**

```
nmap -sV 10.10.10.10
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.10

PORT     STATE    SERVICE    VERSION
22/tcp open ssh OpenSSH 9.x
80/tcp open http nginx
443/tcp open https nginx

Nmap done.
```

**Command:**

```
nmap -sV 10.10.10.30
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.30

PORT     STATE    SERVICE    VERSION
21/tcp open ftp vsftpd 3.x
22/tcp open ssh OpenSSH 9.x
25/tcp filtered unknown
445/tcp open microsoft-ds Samba 4.x

Nmap done.
```

**Expected reasoning:** This is question 3 and question 4 together — services *and* versions, in one pass, on both hosts you've been building a picture of.

**Evidence interpretation:** The web server is now confirmed running `OpenSSH 9.x` and `nginx` — real evidence, not a port-number guess. The file server adds a fourth service entirely: `445/tcp open microsoft-ds Samba 4.x`, a Windows-style file-sharing protocol you'd never have found without the range scan in Exercise 9. Notice port 25 is still `filtered` — service detection can't strengthen evidence about a port it can't even confirm is open.

**Common mistake:** Assuming version detection resolves a filtered port. It doesn't — filtered means the *state itself* is unresolved, and no amount of further probing at that layer changes that on its own.

## 11. Exercise 6 — Interpret and Decide

**Objective:** Exercise 1 found five hosts up out of six. Investigate the one that didn't answer, and decide what it means.

**Command:**

```
nmap 10.10.10.40
```

**Real output:**

```
Starting Nmap
Note: Host seems down. If it is really up, but blocking pings, try -Pn
Nmap done: 0 hosts up.
```

**Command:**

```
nmap -Pn -O -sV 10.10.10.40
```

**Real output:**

```
Starting Nmap

Nmap scan report for 10.10.10.40

PORT     STATE    SERVICE    VERSION
22/tcp open ssh OpenSSH 8.x
8080/tcp open http-proxy Squid 5.x

OS guess: Linux 5.X (embedded)

Nmap done.
```

**Expected reasoning:** This is question 5 and question 6. The first result looked like a dead end; Core Concepts §9 already told you *why* that's not necessarily true, and this is you proving it yourself. Skipping discovery (`-Pn`) and scanning anyway is the "unusual network behavior worth investigating further" the enumeration mindset asks about.

**Evidence interpretation:** This host was never down — it was configured to ignore discovery probes while running two real services: SSH and a proxy on a non-default port (8080, not 80 — a direct, real example of Introduction §5's "a service may run on a non-standard port"). The OS guess (`Linux 5.X (embedded)`) is additional evidence, held with the appropriate confidence from Core Concepts §10 — a strong hint, not a certainty.

**Common mistake:** Accepting "host seems down" as the final answer, and moving on. The single most consequential habit this exercise builds is: **a "down" result is itself evidence worth questioning**, not a stopping point.

## 12. Full Investigation: An Evidence-Based Conclusion

Six exercises' worth of evidence, written up the way a real reconnaissance finding should read — conclusions the evidence actually supports, nothing invented, nothing skipped ahead to:

```
Target:
10.10.10.10 (web01)

Host:
Reachable — confirmed by discovery sweep and direct scan

Open ports:
22/tcp, 80/tcp, 443/tcp

Services:
ssh, http, https

Versions:
OpenSSH 9.x (port 22)
nginx (ports 80 and 443)

Interesting findings:
- The same nginx instance appears to serve both HTTP and HTTPS.
- No other ports responded in the default scan range.

Next investigation:
- The web service (nginx, ports 80/443) is the most promising next
  target — HTTP/HTTPS services are exactly what Web Fundamentals and
  the later Web Pentesting module investigate in depth.
- OpenSSH 9.x is a recent version with no obvious red flag from
  version alone; nothing here suggests SSH is the weaker point on
  this host.
- This conclusion stops at "worth investigating further," not
  "vulnerable" or "exploitable" — this module's evidence supports
  the former, not the latter.
```

Notice the shape: every line traces back to a specific piece of real evidence gathered above. Nothing in "Next investigation" claims a vulnerability or proposes an attack — it identifies where the evidence points, which is exactly as far as reconnaissance and enumeration are supposed to go.

## 13. The Cybersecurity Connection

Nmap sits at a specific place in a much longer methodology:

```
Reconnaissance
      ↓
Enumeration
      ↓
Service identification
      ↓
Vulnerability research
      ↓
Validation
      ↓
Remediation
```

Everything in this module — host discovery, port scanning, service and version detection — supports the **first three stages** of that chain. Nmap tells you what's there and what it appears to be running. It does not research known vulnerabilities for a specific version (that's a separate, deliberate research step), it does not validate whether a suspected issue is real (that requires careful, authorized testing), and it certainly doesn't fix anything. Treating a scan result as if it already answered those later stages is the exact mistake Section 3's enumeration mindset is built to prevent.

This is also exactly why this module exists where it does on the roadmap: everything from here forward — **Wireshark** (watching the traffic these services actually generate), **Burp Suite** and **OWASP Top 10** (investigating the web services this exercise's `nginx` finding pointed you toward), **Metasploit** and the **Red Team** track (the later stages of this same chain) — assumes you can already do what this module just taught: turn a target into a documented, evidence-based picture of what's actually there.

## 16. Common Mistakes

**Jumping from "port is open" to "attack it."** The enumeration mindset stops at "worth investigating further." Section 3.

**Ignoring the ethics boundary because "it's just a scan."** Scan traffic is real, observable, and can trigger real defensive systems. Section 4.

**Treating a "host seems down" result as final.** Exercise 6 is the whole lesson on why that's a mistake worth catching yourself on every time.

**Writing an investigation conclusion that jumps to "vulnerable."** The evidence in this module supports "worth investigating further," not a vulnerability claim — that requires a separate, deliberate research and validation step (Section 13).

**Treating Nmap as the entire methodology.** It's the first three stages of a six-stage chain, not the whole thing.

## 18. Key Takeaways

- The enumeration mindset — alive, open, running, version, unusual behavior, what's next — is the actual structure of a real investigation, not a checklist to rush through.
- Only scan systems you own or are explicitly authorized to test. Every exercise in this module is fully simulated for exactly that reason.
- A "down" or "closed" or "filtered" result is information, not a dead end — each one has a specific, correct meaning, and each one can motivate a next step rather than ending the investigation.
- Widening scope (ranges, all ports) and narrowing focus (specific ports, service detection) are complementary moves, not competing strategies.
- A good investigation conclusion documents what the evidence actually supports — reachability, open ports, identified services and versions, and a next step — and stops there.
- Nmap supports reconnaissance, enumeration, and service identification: the first half of a six-stage security methodology, not the whole thing.
